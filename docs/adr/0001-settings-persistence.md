# ADR-0001 设置持久化：JSON、位置判定与原子写

- 状态：已接受
- 日期：2026-10-18
- 来源：地图 #1；决议 #2；落笔 #8

## 背景

JiuMi 是便携优先的桌面外壳：用户可能把整个程序目录拷到 U 盘、只读共享盘，或者直接放进 `C:\Program Files`。设置（语言、主题、窗口偏好）必须落在一个能解释、能指给用户看的地方，而且不能在不可写时静默失败 ——「改了语言，重启就丢」不可接受。

需要一次定下四件事：用什么格式、放在哪、契约有多稳、写到磁盘上怎么做。

## 决策

1. **格式**：JSON，由 `System.Text.Json` 读写，不引入额外依赖。
2. **位置**：默认 `<exe 目录>\config\settings.json`；启动时探针判定，不可写则**整处**回落到 `%AppData%\JiuMi\settings.json`；两者都不可写才仅内存运行并常驻提示。
3. **契约**：半稳定 —— 缺键补默认、未知键读时忽略写时丢弃、损坏时改名为 `settings.json.bak`、始终写入 `"schemaVersion": 1`。
4. **写入**：同目录临时文件 → 落盘 → 原子替换；接受最后写入者胜，不加跨进程锁。

贯穿四条的一条约束：**配置的读取与写入在任何时刻指向同一个文件**，不存在读一处、写另一处。

## 为什么不是 SQLite、注册表或 INI

衡量标准来自这份数据的形状：几百字节到几 KB、整文件读写、用户会想手改、要能跟着 exe 目录一起搬。

| 方案 | 便携性 | 可手改 | 依赖 | 并发 |
| --- | --- | --- | --- | --- |
| JSON | 优：跟随 exe 目录，整目录拷贝即迁移 | 优：纯文本，可 diff、可进版本控制 | 无：BCL 内置 | 无内建，靠原子替换 + 最后写入者胜 |
| SQLite | 良：文件能搬，但对用户不透明 | 差：需工具打开，手改易损坏 | 重：`Microsoft.Data.Sqlite` + 各 RID 原生库 | 强：事务 / WAL，本场景用不上 |
| 注册表 | 差：Windows 专有，不随目录走 | 差：regedit，不可审查 | Windows 专有 API，需平台分支 | 强：内建事务 |
| INI | 良 | 中：转义、重复键、类型均无标准 | 需第三方解析器或自写解析器 | 无，且无原子写原语 |

**SQLite 输在哪**：它的强项（事务、并发、查询）对应的都是本场景不存在的问题 —— 设置是低频、整文件、用户手动触发的写入。代价却是实打实的：新增原生依赖、构建与分发矩阵变大，而 .NET 已经内置 JSON 和文件 API；文件对用户不可读，「打开文件夹」这个动作也就失去意义；schema 变更要写迁移代码，JSON 只多一次版本分支。用事务换掉一个本来就能用一次原子重命名解决的问题，不划算。

**注册表输在哪**：它是 Windows 专有的，与「配置跟随 exe 目录」的便携模型正面冲突 —— 同一份设置要在每个 OS 上另找落脚点，契约和测试面直接翻倍。它也不可审查：用户看不见，出问题只能远程 regedit，无法进版本控制、无法用文本工具比对。部署语义同样别扭：HKCU 跟用户走而不是跟程序走，换账户设置就分叉；HKLM 又要管理员权限。内建事务是它唯一的强项，而本场景不需要。

**INI 输在哪**：表面最接近，实际输在「没有标准」。.NET 没有内置解析器，要么引第三方包，要么自己写一个解析器并自己测试 —— 后者等于亲手发明一种格式。转义、重复键、全部值皆为字符串、无嵌套，每一条都要额外约定，而这些约定本身就是新的契约负担。相对 JSON，它省下的只是「文件更短」，付出的是类型编码和解析歧义；并发能力与 JSON 相同（都没有），没换来任何东西。

**其他候选**：XML 由 BCL 支持，但冗长、手改噪声大；YAML / TOML 可读性好，却都需要额外依赖，YAML 的隐式类型和缩进规则反而让手改更容易踩坑。JSON 是唯一同时满足「BCL 直接支持 + 手改友好 + 工具链普遍可读」的交集。

## 为什么位置跟随 exe，不可写时整处回落 AppData

**默认跟随 exe，是因为程序目录被当作一个可携带的整体。** 用户拷贝文件夹就完成迁移，符合 U 盘、共享盘的使用方式。AppData 是隐藏的、跟着用户账户走的，与便携模型相反 —— 所以它只能做兜底，不能做默认：一旦默认落 AppData，程序目录就不再是完整的一份。

**用启动探针，而不是等首次保存失败再处理。** 位置必须在首次读取之前确定，因为读写必须同源。若等到保存失败才处理，就会出现「刚从 A 读了值，现在要写 B」的自相矛盾状态：要么丢掉刚读到的值，要么写出一个用户没预期的文件。探针落在启动序列的哪一步由启动序列章节决定，但「先判定、再读取」的顺序不变。

**探针判两件事**：目录可写（建临时文件再删除），以及已存在的 `settings.json` 能以写方式打开。两者都通过才算 exe 侧可用，因为「目录可写但文件只读」是真实存在的状态（只读文件落在可写目录里）。

**整处回落，而不是「读 exe、写 AppData」。** 分开会让「改了没生效」「改完出现在别处」无法向用户解释，也让「我现在的配置到底在哪」没有单一答案。代价是：目录可写而文件只读时，本次会用默认值启动，读不到 exe 侧的旧值。这比「读得到、却永远写不进去」诚实 —— 后者会伪造一个「已保存」。

**不迁移、不合并。** 把 exe 侧旧文件复制到 AppData，等于替用户做了一次数据移动；而下次启动探针若通过，exe 侧又变回权威位置，两个位置会来回抢。宁可本次用默认值，换位置语义的单一。

**两级兜底。** AppData 也写不了时，本次仅内存运行，并给出**常驻可见**提示。这是唯一允许不落盘的情形，且绝不静默 —— 允许它会话内正常操作，但必须让用户知道「这次的修改不会留下」。

**会话中途写失败不回退位置。** 磁盘满、文件被占用、U 盘中途拔出，这些探针都查不出来。此时保持本次会话的位置不变，给一次非阻塞提示「本次更改未能保存」，下次启动重新探针。当场换位置会让用户误以为改动落到了某个文件里。

## 为什么是半稳定契约

**手改是特性，不是漏洞。** 便携应用的配置文件天然会被用户打开：改语言、改路径、复制给别人。所以「一份 JSON 能被手改而不炸」是需求，不是宽容。

半稳定 = **读宽松、写严格、格式带版本**。逐条取舍：

- **缺键补默认**：新版本增加的键在旧文件上自然生效，手改删掉一个键也不致命。替代方案（缺键即报错）会把「少了点什么」升级成「打不开」。
- **未知键读时忽略、写时丢弃**：不必为每个历史版本维护字段清单，拼错的键名也不会被静默带进下一次读取。代价写清楚：用新版本写过的文件回到旧版本打开，旧版本不认识的键会丢（降级不保真）。接受的理由是这些设置都能从设置页重新点回来，而保留未知键需要「保留树 + 合并写」的额外机制，复杂度高于收益。
- **损坏 → `settings.json.bak`**：不静默丢弃用户的文件；单份、每次覆盖，不给磁盘留无限备份；随后用默认值继续启动并给出可见提示。替代方案（校验失败拒绝启动）把一条手误变成打不开程序 —— 对一个外壳应用不成立。
- **`"schemaVersion": 1` 第一天就写**：迁移的锚点。读取时先拿版本再决定解析路径。本期没有第二版，所以「遇到更高版本怎么办」不在这里决定，留给真正引入 v2 的那次改动。

**不做严格校验 + 拒绝启动**：配置文件不是安全边界。任何「一个逗号写错就打不开」的设计，都是拿用户的耐心换开发的确定性。

## 为什么临时文件 + 原子替换，并接受最后写入者胜

要保的是**任何时刻磁盘上都是一个完整文件**；这是正确性问题。而多进程并发写入要不要不丢数据，是策略问题，两者不该混为一谈。

**原地覆写的实际风险**：写入过程中崩溃、断电或磁盘满，会留下半截 JSON；半截 JSON 会被读侧判成「损坏」，触发 `.bak` + 默认值。于是一次写入失败被放大成一次设置丢失。改成「同目录临时文件写完 → `Flush(true)` 落盘 → 重命名替换」之后，读侧只会看到旧版本或新版本，没有中间态。

**同目录是同卷的前提。** 跨卷重命名不是原子操作，会退化成复制 + 删除，原子性当场消失。所以临时文件必须和 `settings.json` 放在同一个目录，而不是系统临时目录。

**原子性由 OS 的同卷重命名提供**（Windows 的 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`、Unix 的 `rename(2)`）。进程崩溃可能留下 `.tmp`，由下次启动清理，不影响读取。

**不加跨进程锁**，理由有三条：

1. 单实例（#7）已经让「两个 JiuMi 同时写」成为少数情况；
2. 锁本身带来一批新失败模式：崩溃后的陈旧锁、超时策略、锁文件落在只读路径、共享盘和跨机器上的锁语义 —— 每一条都要额外设计和测试；
3. 即使加了锁，没有合并逻辑也照样会丢更新。锁只是把「最后写入者胜」换成「等到锁的人胜」，并不提升正确性。

本场景的写入是用户手动触发、低频、整文件几 KB。最坏结果是丢掉一次改动，而不是文件损坏 —— 这个代价可以接受，且被原子替换兜住。

## 后果

**正面**

- 零新增依赖，构建与分发矩阵不变。
- 文件可读、可 diff、可进版本控制，问题现场能直接看。
- 配置位置单一，设置页可以把路径和文件夹直接交给用户。
- 崩溃或断电不会产生半截配置，写入失败不会放大成设置丢失。
- 手改不会导致程序打不开。

**负面（明确接受的代价）**

- 降级丢未知键：新版本写过的文件回到旧版本，旧版本不认识的键会消失。
- 并发写丢更新：最后写入者胜，不加锁。
- 「目录可写、文件只读」时整处切换，本次读到默认值。
- 应用运行中手改文件，下一次保存会整文件覆盖手改内容。
- 没有查询/条件更新能力（相对 SQLite）—— 设置量级不需要。

**中性**

- 损坏时产生单槽 `settings.json.bak`。
- 崩溃可能留下 `settings.json.tmp`，由启动清理。
