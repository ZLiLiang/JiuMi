# ADR-0011 批量重命名：文件模式的多来源批次

- 状态：已接受
- 日期：2026-11-01
- 来源：设计票 [#74](https://github.com/ZLiLiang/JiuMi/issues/74)；规则模型沿用 [ADR-0010](./0010-batch-rename.md)

## 背景

#67 落地后，文件模式仍然只能选一个根目录，并处理该目录（及其子树）里的文件。用户的实际场景经常是「把这几个文件夹里的图、再加上散落在别处的几个文件，一起改名」。

系统对话框不能在同一次多选里同时返回文件和文件夹：`OpenFilePicker` 只返回文件，`OpenFolderPicker` 只返回文件夹。所以「一次选完」在系统对话框里做不到，必须决定批次如何由多次选择拼起来。

## 决策

1. **批次是多来源的，可跨目录、跨盘符**。文件模式下页面维护一个来源列表（`RenameSource`），每次添加形成一个来源项；来源列表只在会话内存在，不写入设置（沿用 #67「所选目录不保存」的决定）。只有直接添加的文件、一个文件夹来源都没有的批次同样合法。
2. **文件夹来源只作扫描容器**。它贡献的是其中的文件，容器目录永不改名；文件模式下直接选中的文件直接入批。文件与文件夹混合改名仍然不做。
3. **入口按模式分叉**。文件模式的页头动作区是「添加」下拉，两项：`添加文件…`（系统文件对话框，可多选、可双击进目录）与 `添加文件夹…`（系统文件夹对话框，可多选，只作扫描容器）。文件夹模式完全不变，仍是单个「选择文件夹」按钮。不应用内自建文件浏览器。
4. **扫描深度用全局开关**。`含子目录` 保持页面级，作用于所有文件夹来源；默认只取第一层。
5. **扩展名筛选作用于所有文件**，包括直接选中的文件。被筛掉的直接文件不静默消失：来源标签显示去重后的净贡献，并额外标明「N 项被筛选」，ToolTip 列出被挡掉的文件名；全被挡掉的来源保留在列表里、显示 `0 / N 项`，不自动移除。
6. **追加语义 + 绝对路径去重**。每次添加追加到末尾；同一路径（大小写不敏感）重复添加静默忽略。同一文件既被文件夹来源扫到又被直接选中时只出现一次，且按**直接文件**对待（显式选择优先于扫描）。父子来源允许并存，重复文件只出现一次，来源标签显示去重后的净贡献，因此重叠加进来的子目录会显示 0 项，由用户自行移除。
7. **排序按来源添加顺序分组，编号全局连续**。组内沿用自然排序（递归时按相对各自来源的相对路径）；直接文件按「一次添加」成组，组内按文件名自然排序，不按点选顺序（系统多选返回的顺序不可靠）。编号仍与预览同序，1..N 连续。
8. **模式切换清空来源**。文件 ↔ 文件夹切换一律清空来源列表、回到空态，必须重新选择。理由：两种模式的来源语义不同（一个是扫描容器集合，一个是唯一根目录），保留半边会让「当前在改什么」变得难以解释。
9. **单一备份根**。开启备份时，以**第一个来源**所在目录的父目录为根，创建 `JiuMi-backup-<时间戳>\`，内部按来源序号分子目录（`1-照片\`、`2-素材\`）；跨盘来源照样复制进去。`RenameBatch.BackupDirectory` 保持单值，日志 schema 保持 1。第一个来源是纯文件来源时，取其中第一个文件所在目录。这一条收紧 [ADR-0010](./0010-batch-rename.md) 决策 4 里「在所选目录之外的同级创建」的表述：多来源下仍只落在一个位置。
10. **拖放同时接受文件与文件夹**（仅文件模式）。拖入的文件夹成为扫描来源，文件成为直接文件来源，一律追加并按第 6 条去重；覆盖层提示改为「松开以添加文件和文件夹」。文件夹模式仍只认目录、只取第一个。非本地项（`TryGetLocalPath` 失败）忽略。
11. **扫描串行、无进度条、无取消**。多个来源依次枚举，沿用现有 `IsScanning` 门控（扫描中禁用执行、来源列表不可编辑、`_scanVersion` 丢弃过期结果），来源行给一句「读取中…」。
12. **预检、撤销、日志语义不变**。目标占用与批内重名一直按绝对路径判定，不同目录的同名文件各自改在自己目录里，不构成冲突。撤销仍是整批一次、逆序、逐项复验、只保留最近一批；撤销后来源列表保留，可再次执行。日志条目已含绝对路径，来源可由路径推导，不新增字段。
13. **行内标注来源目录**。当本批涉及两个及以上不同目录时，预览行的原名称后追加来源目录末段（灰色小字）；只有一个目录时不加。ToolTip 始终给完整路径。同一条件下，执行成功与撤销成功的 InfoBar 不再带「打开文件夹」动作，文案改成一句 `已改名 N 项，分布在 M 个目录`（撤销同构）——「打开哪一个」没有唯一答案。

## 为什么

- **多来源是这个功能的全部意义**。若只允许单目录混合，"把 A、B 两个文件夹的图一起改名"这个真实场景仍然做不到，票就没有价值。
- **文件夹只作容器，是因为容器改名会立刻推翻同批内其它项的相对路径**。ADR-0010 已把「先深后浅」写进顺序约束；把容器也纳入改名会把这条路走成树结构重排，收益远低于风险。
- **两个系统对话框入口胜过自建浏览器**。#74 的痛点本质是「系统对话框一次只能返回一种」，拆成两个入口就解决了；自建浏览器要额外承担路径栏、上一级、盘符枚举、权限目录、键盘导航与无障碍，维护面与这个功能不成比例。
- **筛选对直接文件也生效，是为了让「只处理这些扩展名」这句话成立**。若直接选中的文件绕过筛选，同一个筛选项在不同来源下行为不同，用户无法从界面上预测结果。代价是必须把「被筛掉了几项」显式说出来。
- **去重与净贡献是同一套表达**。父子来源重叠、筛选挡掉、重复添加本质都是「这个来源没有为新批次贡献那么多项」；用一个「净贡献」数字解释，比三种不同的提示更容易理解。
- **按来源分组编号，匹配用户对序号的预期**。混排会让 `{index}` 与「我先加的是这批」矛盾；而点选顺序又不可靠，所以组内按文件名排。
- **模式切换清空，是因为两种来源语义不可通约**。保留第一个作为根目录看似贴心，实际会让用户在文件夹模式下看到自己没选过的范围；清空是唯一不会误导的选项。
- **单一备份根，让用户在日志或文件夹里只需记一个位置**。每个来源各建备份会散出若干时间戳目录，清理时容易漏；单根内部按来源分子目录既保住了分组，也保住了「一个路径」。
- **跨目录同名不冲突，是绝对路径判定的自然结果**，不需要为多来源写特例。

## 备选与取舍

| 备选 | 为什么没选 |
| --- | --- |
| 单目录混合（仍只选一个工作目录） | 做不到跨目录批次，等于没解决 #74 的动机 |
| 自建应用内文件浏览器，一个列表里同时勾选文件和文件夹 | 额外承担导航、盘符、权限、无障碍与 i18n；两个系统对话框入口已覆盖同一需求 |
| 必须有且只有一个文件夹来源，文件来源不限 | 用户「只想挑 5 个文件改名」时被迫先选一个不关心的目录 |
| 扩展名筛选只作用于扫描结果 | 同一筛选在不同来源下行为不同，界面无法自证 |
| 添加时拦截父子重叠来源并提示 | 父来源是否递归取决于全局开关，预判会误报 |
| 全局按文件名混排编号 | 与「我按这个顺序加的」冲突，`{index}` 难以预测 |
| 模式切换保留第一个文件夹来源 | 会让用户在另一模式下看到自己没选过的范围 |
| 每个来源父目录各建一个备份目录 | 一次执行散出多个时间戳目录，清理容易漏；批次模型还要改成列表 |
| 多来源时禁用物理备份 | 直接砍功能 |
| 日志升 schema 2 增 `sources` | 条目已含绝对路径，来源可推导；升级会给用户已导出的对照增加噪音 |
| 扫描加进度条与取消 | 本地目录枚举通常秒级；引入取消要处理「取消后已扫到的一半」的状态 |
| 来源列表持久化到设置 | 路径经常失效，且与 #67「所选目录不保存」的决定冲突 |
| 来源内单独移除某个文件 | 需要一棵树控件；正确做法是把文件从选择里排掉 |

## 后果

- `RenameScanRequest` 从「一个目录」变成「一组来源」，`RenameScanner` 对每个来源产出候选并带上来源标识；`RenameCandidate.RelativePath` 相对各自来源计算。
- `RenameExecutionRequest.SourceRoot` 改为备份根语义（`BackupRoot`），由 UI 从第一个来源推导。
- `RenamePlanner` 仍保持纯函数，排序键改为「来源顺序 → 组内自然排序」；跨目录同名不产生预检错误。
- 来源列表成为页面状态的一部分：追加、整批移除、清空、扫描中只读；模式切换即清空。
- 预览行在跨目录时多一段来源目录文字，列表行高不变。
- 新增文案键集中在 `Tool.FileRename.Source.*`、`Tool.FileRename.Add.*`，`Drop.Hint` 与空态说明改写。
- 备份目录内部多一层按来源编号的子目录，备份根仍只有一个。

## 不在本 ADR 内

- 文件夹模式的任何改动。
- 文件与文件夹混合改名。
- 应用内自建文件浏览器。
- 来源内单独移除某个文件；来源列表持久化。
- 扫描进度条与取消。
- 日志 schema 2 与来源段。
- 起始序号、跨目录移动、后台监听：同 ADR-0010。
