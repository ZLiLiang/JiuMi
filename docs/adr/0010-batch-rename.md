# ADR-0010 批量重命名：一份规则模型、预检不修补、撤销而非备份

- 状态：已接受
- 日期：2026-10-31
- 来源：README 路线图「批量修改文件夹下文件名称」；实现票 [#67](https://github.com/ZLiLiang/JiuMi/issues/67)

## 背景

用户要给一个文件夹里的文件或文件夹批量改名。旧项目 `JiuMiTool` 的 `JiumiTool2` 分支只作业务参考：模式二选一、输入一串字符并多选两个当定界符、用 `首字符 + ".*?" + 末字符` 拼正则、把匹配段换成递增序号、跳过名字含「备份」的项。它没有预览、没有冲突判定、没有撤销，任一文件失败就整批停在中途。

旧交互有三处不能保留：

1. **定界符拼正则不可读也不可预测**。用户选两个字符，实际得到的匹配范围由正则引擎决定，名字里的元字符会改变行为。
2. **备份目录落在所选目录内**，下一次扫描会把备份当成待改名素材。
3. **批量操作没有预览与撤销**。改名是破坏性操作，没有执行前确认和事后恢复，失败只能人工善后。

## 决策

1. **一份规则模型，两个入口**。业务层只有 `RenameRule`：`Replace`（字面量或正则查找替换，替换串可含 `{index}` / `{index:00}`）与 `Template`（整名模板 `{name}`、`{index}`、`{ext}`、`{date}`）。页面的 `普通` / `进阶` 只是输入方式；普通三个任务由 `RenameRuleConverter` 换算成同一份 `RenameRule`，编号、排序、预检、预览只有一套实现。
2. **编号跟预览顺序**。文件按相对路径自然排序（不区分大小写，数字按数值）；文件夹先深后浅。编号从 1 开始，`{index:00}` 的补零宽度取「显式宽度」与「本批条目数十进制位数」的较大值；`{index}` 不补零。
3. **预检不静默修补**。目标名依次检查为空、非法字符与控制字符、尾部空格或点、Windows 保留名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）、长度（名字 255、完整路径 260）、批内重名、目标已存在。任一命中即标红该行、在页内汇总并禁用执行；不自动替换字符、不自动加序号、不跳过冲突项。
4. **优先撤销，备份默认关闭**。只保留最近一次批次的内存撤销。撤销前逐项复验：文件或文件夹仍在、类型一致、文件长度与最后写入时间（文件夹只比最后写入时间）与执行后记录一致；目标原名未被占用。任一项不满足则该项撤销失败并保留改名后的状态，其余项照常恢复。物理备份是可选保险：默认关闭，开启时在所选目录之外的同级创建 `JiuMi-backup-<yyyyMMdd-HHmmss>`，逐项复制；备份失败的那一项不改名。
5. **范围与跳过**。文件 / 文件夹一次只做一种；默认只处理第一层，可选「包含子目录」；扩展名筛选只决定哪些文件进入扫描，不改扩展名。所选目录本身永不进入候选。隐藏、系统属性项与符号链接、目录联接跳过并在跳过面板单独列出，不跟进链接；只读属性不阻止改名。
6. **分层**。`JiuMi.Application` 持有纯函数（规则、`RenamePlanner`、预检错误、批次与日志模型）；`JiuMi.Infrastructure` 实现扫描、执行、目标占用探测与日志写入；`JiuMi` 只做绑定、对话框、拖放与页面编排。`RenamePlanner` 不读文件系统，目标占用通过 `IRenamePathProbe` 返回的判定函数传入。
7. **失败语义**。预检错误是页面内容，不弹 InfoBar。执行期单文件失败继续整批，逐项生成一条 `ErrorRecord`（未登记呈现，只进日志与详情缓冲），结束时汇总一条 InfoBar；部分失败给出警告与次行说明。无匹配时显示 0 项受影响并禁用执行，不写错误记录。

## 为什么

- **一份规则模型是唯一能同时满足「普通可读」与「进阶可写」的结构**。如果普通任务另建一套实现，编号、排序、预检、预览会出现两套边界；换算成模板与查找替换后，普通模式只是受约束的输入面板。
- **预检拒绝修补，是因为批量改名最贵的错误是「改错了一批」**。自动替换非法字符会让用户看到与输入不同的结果；自动加序号会让预览与确认文案失去意义。把原因摆出来并禁用执行，用户改规则后重跑，代价最低。
- **撤销比备份更贴近用户预期**。备份占用磁盘、需要用户事后自己去翻；内存储存新旧名对照，撤销是一步操作。复验文件长度与写入时间挡住了「外部程序改过文件后撤销覆盖」这一最危险的场景。
- **备份放在所选目录之外**，是为了切断「备份被下一次扫描当成素材」这条旧实现的循环。
- **文件夹先深后浅**是改名顺序的硬约束：先改父目录会让子项的路径失效；先改子项再改父项，预览里的相对路径才能保持可读。
- **跳过链接而不跟进**，避免把链接目标改名、也避免目录联接造成遍历环。

## 备选与取舍

| 备选 | 为什么没选 |
| --- | --- |
| 保留旧「选两个字符当定界符」 | 匹配范围由正则元字符决定，用户无法从界面预测结果；票面明确不做 |
| 普通任务单独实现一套业务规则 | 编号、排序、预检会出现两套边界，预览与执行容易分叉 |
| 预检自动修复非法字符 / 自动加序号 | 静默改变用户输入，破坏确认文案的可信度 |
| 只做备份、不做撤销 | 备份默认会占空间，且撤销需要用户自己翻目录；票面要求撤销 |
| 默认开启物理备份 | 复制整棵树可能远超改名本身的耗时与空间；票面定为默认关闭 |
| 支持跨目录移动、正则捕获组反向引用 | 超出「改名」范围；票面明确不做 |
| 多步撤销与历史批次倒带 | 需要持久化操作历史与文件指纹，v1 只保留最近一次批次 |
| 复制时跟进符号链接 | 会把链接目标的内容复制进备份，甚至形成环 |

## 后果

- 改名规则只有一种业务表示，普通 / 进阶切换按换算规则带入参数；两套参数都进设置，切层级不丢输入。
- 目标占用需要一次文件系统探测；`RenamePlanner` 保持纯函数，测试用谓词模拟。
- 撤销依赖内存批次，进程退出后消失；需要长期留痕的用户导出 JSON 日志。
- 只读项照常改名；隐藏与系统项不参与，也不会被「包含子目录」带进来。
- 备份目录名带时间戳，已存在时追加 `-2`、`-3`；备份复制跳过内部链接。

## 不在本 ADR 内

- 正则捕获组反向引用（`$1`）：票面明确不做。
- 改大小写、加日期前缀等新普通任务：等有需求再加。
- 起始序号不是 1：需要改业务契约，暂不做。
- 跨目录移动、修改文件内容或元数据：只改名。
- 后台监听目录并自动改名：不做。
- 像素级页面排版：见 [`docs/ui-spec.md`](../ui-spec.md) 的「批量重命名」节。
