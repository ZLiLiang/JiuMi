# ADR-0003 错误呈现：两级模型、四类载体、详情即日志记录

- 状态：已接受
- 日期：2026-10-18
- 来源：地图 #1；决议 #6；落笔 #12

## 背景

应用外壳有多条失败路径：配置落点回退、设置文件损坏、语言或主题切换失败、GIF 加载失败、初始化超时、初始化抛异常、主窗口建不出来、UI 线程上的未捕获异常。本期不建完整日志设施，但每条失败都得回答「用户看到什么」。

需要一次定下五件事：错误分几级、用什么载体、详情从哪来、全局异常钩子怎么分工、平台专属 API 允许到什么边界。

## 决策

1. **只分两级**：非阻断与阻断。判定只看「主窗口是否可用」，不看异常类型或调用方自报的严重程度。
2. **四类载体**：全局 InfoBar（默认）、容器内占位（局部资源失败）、独立错误窗口（阻断，以及主窗口可用时的 UI 线程未捕获异常）、系统通知端口（无可见窗口时兜底）。
3. **详情即一条错误记录**：`timestamp` / `level` / `code` / `operation` / 异常三件套 / `appVersion` / `osDescription` / `configPath` / `count`，来源是最近 50 条的内存环形缓冲。本期只把致命错误落成文本崩溃文件。
4. **三个全局钩子分工**：`Dispatcher.UIThread.UnhandledException` 走错误窗口并标记 handled；`AppDomain.UnhandledException` 只尽力写崩溃文件；`TaskScheduler.UnobservedTaskException` 记 Warning 不弹 UI。退出码正常 `0`、致命 `1`。
5. **平台专属 API 允许使用，但必须隔离在 Infrastructure**：`IUserNotification` 在 Application，Windows 实现在 Infrastructure，其他平台 no-op；`#if WINDOWS` 只允许出现在 Infrastructure 与 Desktop 组合根。

完整场景映射、字段表与线程规则见 [`docs/architecture.md`](../architecture.md) 的「错误呈现与诊断」章节；尺寸、间距与排版见 [`docs/ui-spec.md`](../ui-spec.md)。

## 为什么只分两级

等级必须对应**不同的用户契约**，否则它只是颜色深浅。

票里原本设想的三级是「可恢复 / 功能失败 / 致命」。前两者在用户侧是同一件事：界面还在、这次操作没成、其余功能可用。区别只落在文案与有没有「重试」，不构成两套行为。所以合并为非阻断。

剩下的分界只能是「还能不能继续用」，而这件事有一个可观测的判定：**主窗口是否存在且可用**。用它判级的好处是稳定 —— 不需要调用方在抛错时自报严重程度，也不会因为某处自报得过于悲观或乐观而漂移。代价是级别与日志级别不再一一对应：一条记录可以是 Warning 级日志却触发阻断窗口（如主窗口构造失败），这被视为可接受，因为二者服务不同读者。

## 为什么不用 `ContentDialog`

- **没有 owner**：本期唯一的阻断场景发生在启动期，主窗口还不存在。`ContentDialog` 需要一个宿主，在启动期无处可挂。
- **与已定决议冲突**：启动期不弹模态（#4 / [ADR-0002](./0002-splash-startup-sequence.md)），配置回落也不打断用户（#2 / [ADR-0001](./0001-settings-persistence.md)）。
- **与异常钩子冲突**：在 `UnhandledException` 里弹模态会重入消息循环，异常处理路径反而变成新的失败点。
- **结论**：阻断用一个不依赖主窗口的独立窗口，非阻断用 InfoBar，两者都不需要 owner。

状态栏同样被排除：外壳没有常驻状态区，为报错单独造一条，既占空间又要维护一套与 InfoBar 并行的心智模型，不划算。

## 为什么「详情即日志记录」

面向用户的详情与面向排障的日志如果各建一份数据结构，必然分叉：字段增加时改一处漏一处，用户复制出来的内容与日志对不上，最后没人对账。

用同一条记录同时满足三个读者：

- **用户**：点「复制详情」拿到可粘贴给开发者的文本。
- **开发者**：同一组字段在日志里可查、可 grep。
- **测试**：字段与 `code` 映射可以被单测断言（见本地化章节单测第 5 项）。

代价是日志设施未落定时就得先冻结字段，因此 warning / error 本期只进内存缓冲，完整设施（文件 sink、滚动、级别过滤、脱敏、诊断导出）由 #11 承接；崩溃文件例外，它必须在日志设施之前就能写。

50 条的上限取的是「用户看到提示 → 反应过来去点复制」的窗口，同时保证内存有界。

## 为什么平台 API 允许但必须隔离

系统通知与崩溃文件路径都是平台专属的。纯跨平台实现意味着放弃「窗口不可见时仍能告知用户」，而单实例与托盘一旦落地，窗口不可见会成为常态。

允许使用不等于允许散落：

- 抽象放 `JiuMi.Application`，UI 只依赖抽象，可以在测试里注入假实现。
- 实现放 `JiuMi.Infrastructure`，`#if WINDOWS` 只出现在 Infrastructure 与 Desktop 组合根。
- 后果是边界可按目录审查：UI / Application 里出现 `#if WINDOWS` 即为违规。

这条同时修订了地图笔记里原先「UI / Application 不写平台专属 API」的绝对表述。

## 备选与取舍

| 备选 | 为什么没选 |
| --- | --- |
| 三级模型 | 前两级用户契约相同，多一级只增加文案与样式分叉 |
| 统一用 `ContentDialog` | 启动期没有 owner，且在异常钩子里会重入消息循环 |
| 结构化详情面板 | 需要另建 UI 与字段映射；复制文本已足够开发者定位问题 |
| 只写日志、不打扰用户 | 「设置没保存」「切语言失败」必须让用户知道，否则表现为静默失效 |
| 详情塞在 InfoBar 里展开 | InfoBar 是跨页常驻的窄条，展开会把内容顶走；独立窗口才有空间放堆栈 |

## 后果

**正面**

- 每条失败路径都有确定的可见结果，且阻断只在真的无法继续时出现。
- 用户复制的内容与日志、单测共用一套字段，不会分叉。
- UI 与 Application 不依赖平台 API，测试与将来移植都不必改动上层。

**负面（明确接受的代价）**

- 本期 warning / error 只存在内存里，进程退出即丢；排障依赖用户当场复制。
- 出现两个窗口形态（splash、主窗口、错误窗口）需要各自维护焦点与关闭语义。
- 错误窗口文案内嵌 zh-CN，非中文用户在阻断场景下仍看到中文。
- `code` 与 `Error.<code>` 文案键必须手工保持一一对应，靠单测兜住。

**中性**

- 系统通知端口本期没有真实触发点（没有后台任务），只是先把端口建好。
- 错误窗口每进程只允许一个：已在显示时再致命，写日志后直接退出。
