# ADR-0004 日志：Serilog 写 JSON Lines、崩溃文件独立、不外发

- 状态：已接受
- 日期：2026-10-18
- 来源：地图 #1；决议 #11；落笔 #15

## 背景

错误呈现已经把用户能看到的「详情」定义为一条错误记录（[ADR-0003](./0003-error-presentation.md)），但它只在内存里：进程一退就没了，排障只能靠用户当场点「复制详情」。应用外壳已经有足够多需要在事后查的路径——启动状态机、配置探针与回落、设置读写、语言与主题切换、单实例激活、托盘过渡、全局异常钩子。

需要一次定下：用什么写、写到哪、留哪些级别、什么格式、写失败怎么办、保留多久、脱敏到什么程度、能不能导出与外发。

本 ADR 只定**日志设施**。错误记录的字段与呈现归 ADR-0003；配置落点判定归 ADR-0001；控件形态归 `docs/ui-spec.md`。

## 决策

1. **日志用 Serilog 4.4.0**，只带三个配套包：`Serilog.Sinks.File` 7.0.0（文件）、`Serilog.Formatting.Compact` 3.0.0（紧凑 JSON）、`Serilog.Sinks.Debug` 3.0.0（仅 DEBUG 构建）。
2. **Application 直接依赖 `Serilog.ILogger`**；`LoggerConfiguration` 只在 Desktop 组合根与 Infrastructure 组装，UI 不引用 sink 类型。
3. **落点跟随配置启动探针**：`<exe 目录>\logs\`，exe 侧不可写时 `%AppData%\JiuMi\logs\`；与 `config\` 同级，绝不进 `data\`。
4. **五级 + 环境变量覆盖**：发布默认 `Information`，`JIUMI_LOG_LEVEL` 可覆盖，设置页不提供级别开关，级别不写入 `settings.json`。
5. **Compact JSON Lines**：`jiuMi-yyyyMMdd.jsonl`，按天 + 5 MB 滚动，最多保留 30 个文件。
6. **同步、unbuffered 写入**，`Fatal` 立即刷盘；写失败只降级成「关于」区的状态，不弹提示。
7. **崩溃文件独立**：沿用 ADR-0003 的纯文本 `crash-*.txt`，不并入统一 sink。
8. **脱敏只做一件事**：用户目录前缀替换为 `%USERPROFILE%`；文件日志、「复制详情」、诊断包共用。
9. **诊断包手动导出**：设置页「关于」区，BCL `ZipFile` 打包，零额外依赖。
10. **不外发**：崩溃报告、日志、诊断包一律留在本机。

完整字段表、滚动参数与目录规则见 [`docs/architecture.md`](../architecture.md) 的「日志与诊断」章节。

## 为什么是 Serilog，而不是 MEL 桥接或自造接口

三个选项的能力边界不同，但真正拉开差距的是**谁写滚动逻辑**：

| 选项 | 代价 |
| --- | --- |
| 自造 `ILogger` 接口 + 自写文件 sink | 滚动、格式化、级别过滤、文件命名冲突、跨天边界都得自己写并自己验证；最终产出一个功能更少、没有实战检验的 Serilog |
| `Serilog.Extensions.Logging`（MEL 桥接） | 项目不用 Host 的 logging builder，也没有消费 `ILogger<T>` 的第三方库；桥接只增加一层抽象，还要在 MEL 与 Serilog 两套级别命名之间翻译 |
| 直接用 `Serilog.ILogger` | 依赖少，接口即契约；测试可注入无 sink 的 logger，不必为日志再造一个测试替身端口 |

选第三条。日志是旁路，它不该成为 Application 里又一个需要维护的抽象层；而滚动与格式化恰恰是第三方实现的强项。

## 为什么只要最少组件

- **不用 Async sink**：异步队列换来吞吐，代价是一个后台线程、退出时的刷盘协调，以及崩溃时队列里尚未落盘的事件——而那正好是要查的那一批。桌面外壳的日志量（每次用户操作几条）用不上这个吞吐。
- **不用 `Serilog.Settings.Configuration` / `.AppSettings`**：日志必须在配置探针**之前**可用，因为探针结果本身要记日志。让日志配置去读 `settings.json`，会形成「日志等配置、配置失败要日志」的启动期循环依赖。
- **用 `Serilog.Sinks.Debug` 而不是 `Debug.WriteLine`**：两条输出路径必然分叉；DEBUG 构建把同一个 sink 挂进同一条事件流，保证调试器里看到的就是写进文件的事件。

## 为什么放弃「保留 14 天」

按时间保留读起来更自然，但稳定版 `Serilog.Sinks.File 7.0.0` **没有** `retainedFileTimeLimit`（只有 `dev` 分支有）。要按天保留只有两条路：把核心依赖押到预发布分支，或自建清理器在启动时扫描并删除目录。前者的风险不划算，后者等于把 sink 的滚动语义拆成两半。

改用文件数上限：30 个 × 5 MB ≈ 150 MB 硬上限，对桌面应用足够；每个事件自带 UTC 时间戳，按时间找日志仍然可行。

## 为什么脱敏只替换用户目录

日志的价值在路径、异常消息与堆栈。把 URL、文件名一律打码，等于把排障最需要的信息删掉，而换来的只是本地文件的额外保险。

边界因此收窄成两条：

- **替换**用户目录前缀（它包含账号名，是最直接的隐私信息）。
- **不记录**设置值、凭据与文件内容（它们根本不该进日志，而不是进日志后再打码）。

因为「不外发」是硬边界，这条规则的风险面止于本机文件；一旦将来要外发，脱敏需要重新设计，与上传一起单独立项。

## 为什么诊断包是手动步骤

自动上传需要同意流程、隐私说明与服务端，本期一样都没有。手动导出把决定权留给用户，也让「不外发」这条边界可以被验证：代码里没有任何网络出口。

导出失败按非阻断处理：错误进 InfoBar，详情可复制，不阻断任何正在进行的操作——导出本来就是排障手段，不该成为新的故障点。

## 备选与取舍

| 备选 | 为什么没选 |
| --- | --- |
| 纯文本日志 | 字段化查询与结构化 grep 都不如 JSON Lines；Compact JSON Lines 一行一事件，`grep` 依然可用 |
| 自造日志接口 + 自写 sink | 重造滚动与格式化，边界条件没有实战检验 |
| MEL 桥接 | 没有消费 MEL 的第三方库，多一层抽象不换来能力 |
| `Serilog.Sinks.Async` | 桌面量级用不上；崩溃时队列里的事件可能丢 |
| `Serilog.Settings.Configuration` | 日志在配置探针之前就要就绪，读配置会形成循环依赖 |
| 按天保留（14 天） | 稳定版 sink 无 `retainedFileTimeLimit` |
| 崩溃文件并入统一 sink | 崩溃时日志管道可能已损坏；独立纯文本写入路径更短、失败率更低 |
| 设置页提供日志级别开关 | 会把易变偏好塞进半稳定契约，且用户无从判断该选哪一级 |
| 诊断包自动上传 | 需要同意与隐私设计、服务端；本图不做 |

## 后果

**正面**

- 只有一条事件流：调试器、文件日志与错误详情的字段对得上。
- Application 只依赖接口，替换实现或注入测试替身不需要改上层。
- 磁盘占用有确定上限，不依赖任何后台清理。
- 「不外发」是可审查的：没有上传代码，也就没有隐性的隐私面。

**负面（明确接受的代价）**

- 多出四个 NuGet 依赖，且它们的目标框架是 `net8.0`（在 `net10.0` 上兼容，但不是原生目标）。
- JSON Lines 对用户不可读，排障需要工具；这是为结构化付的代价。
- 级别只能靠环境变量调整，用户侧看不到也改不了。
- 按文件数淘汰意味着排障窗口与事件密度挂钩：日志越密，可回溯的时间越短。
- 日志写失败时用户只看到「关于」区的一行状态，没有主动提示——这是刻意的，日志不该打断功能。

**中性**

- 诊断包是手动步骤，需要用户配合。
- 崩溃文件与日志文件是两条独立的写入路径，各有自己的保留数。
