# ADR-0002 splash 启动序列：应用计时、两道门与降级阶梯

- 状态：已接受
- 日期：2026-10-18
- 来源：地图 #1；决议 #4；落笔 #10

## 背景

JiuMi 启动时先显示一个无边框 splash，播一遍 `splash.gif`，然后进主窗口。三条需求彼此拉扯：

- GIF **只播一遍**，播完必须真的停；
- 初始化（DI 容器、配置探针、设置加载、本地化、主题）可能比 GIF 快，也可能比 GIF 慢；
- 用户不该看到一闪而过，也不该被 splash 拦住。

需要定的是：谁决定 splash 何时退场、拿什么保证「只播一遍」、初始化卡住时怎么办、资源缺失或初始化失败时降到什么。

本 ADR 只定**启动序列**。splash 的尺寸、进度环形态与淡变曲线参数属于 UI 规格；错误呈现、日志设施与单实例各有专章。

## 决策

1. **显式状态机**：`Bootstrapping → SplashShown → Animating → Waiting → Handoff → Running`，失败为终态 `Faulted`。完整状态表与每一态的进出条件见 `docs/architecture.md` 启动序列章节，本 ADR 只记录为什么是这些状态。
2. **两道门取晚者**：`max(1000ms, GIF 时长)` 与「初始化就绪」两者都满足才交接；就绪另有 10000ms 兜底，到点强制交接。
3. **单次播放由应用计时**：`IterationCount` 保持 `Infinite`，应用按帧延时累加，到点把 `Source` 置空。
4. **资源四档降级**：GIF → 静态 poster → 纯背景 + 进度环 → 不显示 splash。
5. **交接用交叉淡变**：主窗口以 `Opacity = 0` 先显示在 splash 之上，200ms 同时淡变。
6. **启动期不阻塞、不弹模态、不允许跳过**：失败一律记下来，主窗口出现后再以 InfoBar 呈现。

## 为什么单次播放由应用计时，而不是 `GifImage.IterationCount`

`Avalonia.Labs.Gif 12.0.2` 的 `GifImage` 没有 `AnimationCompleted`、没有 Play/Stop/Pause、没有播放状态属性，唯一可用的控制就是 `IterationCount`。而这个属性表达不了「恰好一遍」：

- 迭代判断是 `_iterationCount > IterationCount.Value`，且只在帧索引变化时更新 → 设 `N` 实际播 **`N+1`** 遍。设 1 得到两遍。
- 单帧 GIF 因帧索引始终不变，**永远不会停止**。
- 播完是**停止绘制**，不是定格末帧 —— 所以「播完停在最后一帧」这个常见诉求在控件层不存在，任何依赖它的写法都会在某类素材上翻车。
- GIF 内嵌的 NETSCAPE 循环次数被解析但从不使用，素材里写的「播放一次」不算数。

用 `Infinite` + 自己按帧延时累加，换来三件事：可预测的结束时刻、与就绪状态取晚者所需的「剩余时长」、以及不依赖未文档化的第三方行为。代价是自己维护计时，但计时规则只有一条（按帧延时累加），比围着控件语义做兼容便宜。

还有一个副作用必须写下来：**渲染期的 LZW 解码错误发生在合成线程**，被 Avalonia 内部捕获并只写日志，应用拿不到。所以「解码失败要降级」只对**构造与头部解析**成立 —— 运行中解码失败表现为 GIF 区停在上次绘制的画面，计时照常推进。把它写进 ADR，是为了避免将来有人把它当成可修的分支反复排查。

## 为什么有 1.0 秒的下限

splash 的作用是「说明程序在启动」。短于一次视觉处理的展示（几百毫秒）只让人看到闪烁，反而像卡了一下；1000ms 是「看不清内容、但明确意识到发生了什么」的下限，同时短到不构成等待。

它只是**下限**，不是固定时长：GIF 本身长于 1 秒就以 GIF 时长为准，不截断。截断会让动画停在半截，用户对「动画没放完就没了」的感知是卡顿，不是快。

## 为什么 10 秒兜底之后仍应用迟到的初始化

兜底的目的是**不让初始化无限期扣住窗口**，不是「初始化作废」。初始化在第 10 秒之后完成时：

- 丢弃结果 → 程序停在默认主题 / 默认语言，用户改过的设置看起来「没生效」，且无法自行解释；
- 退出重启 → 用一次重启惩罚一个慢磁盘。

所以迟到的结果照常应用：主题与语言都走既有的热切换路径，不需要额外机制。代价是用户可能看到界面在进入主窗口后变色或变语言 —— 这比「设置静默失效」诚实。同时记一条 Error，让「这次启动很慢」在日志里有据可查。

10 秒本身没有理论依据：它远大于正常初始化的量级（一次探针加几个 JSON），又小到用户还愿意等。它是一条兜底，不是目标。

## 为什么不弹模态、不允许跳过

**不弹模态**：启动期的模态需要一个 owner 窗口，而此刻只有 splash；一旦有未关闭的模态，主窗口的淡变就无法开始，整个交接链路被卡住。所以启动期的一切失败都先记下来，主窗口出现后再呈现（两级错误模型的非阻断类，见「各类错误发生时用户应该看到什么？」）。

**不允许跳过**：GIF 只播一遍、下限 1 秒，跳过能省下的时间上限就在 1 秒量级；而真正可能拖住用户的是初始化，跳过按钮也无法越过就绪门槛。为 1 秒的收益引入一条交互路径与一整套焦点、可访问性规则，不划算。

## 为什么资源降级是这四档

- **① GIF**：首选，唯一带动画的表达。
- **② 静态 poster**：GIF 缺失或**构造期**异常时，仍要有品牌表达。异常只能按 `Exception` 兜住 —— `GifStreamSource` 的异常类型是 internal，抓不到具体类型，也不该按消息文本匹配。
- **③ 纯背景 + 进度环**：poster 也没有时不假装有素材；纯背景保证底色一致、不闪白，进度环保证「它在动」。
- **④ 无窗口**：splash 窗口本身建不出来时，最稳的降级是不显示 splash，静默等就绪（10s 兜底）后直接进主窗口。此时没有窗口可淡变，交接退化为一次显示，`ShutdownMode` 与 `MainWindow` 的约束不变。

降档只写日志，不打扰用户：素材缺失不是用户的错，也不是用户能修的东西。

## 后果

**正面**

- splash 的退场时刻是一个可推演的表达式，不是若干定时器互相竞争。
- 「只播一遍」不依赖第三方控件的未文档化行为，升级该包不会悄悄改变启动时序。
- 任何一档素材缺失都有确定表现，不会黑屏或卡死在 splash。
- 慢初始化不再永久扣住窗口，且迟到的结果仍然生效。

**负面（明确接受的代价）**

- 运行期 GIF 解码失败不可控，表现为画面停在上一帧。
- 启动超过 10 秒的用户会看到主题或语言在进入主窗口后跳变一次。
- 没有跳过路径，最快的启动也要 1 秒。
- 状态机多出 `Waiting` 态与一条兜底分支，测试面比「定时器到点就进主窗口」大。

**中性**

- `Handoff` 期间两个窗口同时存在，主窗口以 `Opacity = 0` 先显示。
- 主窗口必须早于 `Handoff` 构造完成并赋给 `MainWindow`，否则 `ShutdownMode = OnMainWindowClose` 会在关闭 splash 时结束进程。
- splash 窗口必须使用不透明背景，否则 GIF 的 alpha 会被 `AlphaFormat.Opaque` 渲染成黑。
