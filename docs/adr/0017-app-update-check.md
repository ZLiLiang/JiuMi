# ADR-0017 应用更新检查：双源 Release 清单、通道跟随与只提示策略

- 状态：草案
- 日期：2026-11-22
- 来源：设计讨论定稿；实现票 [#181](https://github.com/ZLiLiang/JiuMi/issues/181)；与世界时钟在线更新同一模式（[ADR-0008](./0008-world-clock-catalog.md)）

## 背景

JiuMi 以自包含 win-x64 ZIP 分发，Release 手工创建，版本号唯一来源是 `Directory.Build.props`。应用没有任何更新检查，用户只能自己回到仓库发现新版本；`build-and-verification.md` 把 auto-update 列为范围外。

目标用户主要在国内：GitHub 的 Release 下载经常不可用或极慢，而 Gitee 的公开仓库 API 与 Release 附件在匿名访问下可用（已实测）。单纯实现「GitHub 检查更新」会把用户引向一个下不动的链接。

同时，项目既发稳定版也发预览版，装机版本可能本身就是 `1.4.0-preview.1`；通道规则必须避免「预览版用户收不到任何提示」和「稳定版用户被塞预览版」两种错误。

## 决策

1. **只提示，不自动安装**：v1 只做检查、提示和跳转 Release 页面。应用内下载、替换文件、重启与回滚不在本版；全自动更新是后续目标。
2. **双源发布、双源检查**：清单与 ZIP 同时发布到 GitHub 与 Gitee；检查时两个源都请求（Gitee 优先，单源超时不阻塞另一源），在所有可达结果中按 SemVer 取最大值；「前往下载」打开给出该版本的那一侧的 Release 页面。
3. **固定清单位置**：每个 host 一个固定 tag `app-update` 的已发布 Release，资产名固定 `update.json`，每次发版覆盖；不走 GitHub REST API（未认证限流、`/releases/latest` 忽略预发布、`api.github.com` 在国内不稳定）。
4. **清单同时承载两个通道**：`stable` 与 `preview` 两个条目，字段为 `version / prerelease / publishedAt / pageUrl / assetUrl / assetSha256 / assetSize`，条目可为 `null`。哈希与大小是给后续自动更新预留的。清单在资产上传完成之后**最后上传**，保证不指向不存在的文件；未更新的通道从该 host 的 Release 历史回填（Gitee 首次上传时从 GitHub 补）。
5. **通道跟随安装版本**：稳定版安装只看 `stable`；预览版安装看 `stable ∪ preview` 中较新者，因此 `1.4.0-preview.1` 能升级到 `1.4.0`。比较使用完整 SemVer（含预发布排序），只提示更高版本，永不提示降级；不新增通道设置项。
6. **检查节奏**：壳可见约 30 秒后检查一次，之后按「上次检查 + 24 小时」一次性排下一次；不使用周期轮询。检查状态（`lastCheckedAt`、`lastNotifiedVersion`）写入独立缓存 `updates/state.json`，不写 `settings.json`，避免每次检查都触发设置变更传播。
7. **开关语义**：后台检查受 `OnlineDataEnabled` 控制；手动「检查更新」不受开关限制。后台失败静默（Warning 日志），手动失败在关于页显示「检查失败 + 重试」。
8. **关于页交互**：版本号下方一行状态（检查中 / 已是最新 + 上次时间 / 新版本可用 / 失败 + 重试），操作行新增「检查更新」按钮，有更新时变「前往下载」。状态与入口都留在关于卡片内，不弹窗、不新增页面。
9. **通知**：发现新版本弹一次托盘气泡，复用 `IUserNotification`（`WindowsTrayIcon` 的 NIIF_INFO 实现），点击打开 Release 页面；同一版本只弹一次，手动检查不弹气泡。主窗口可见时也照弹，并同步更新 `IUserNotification` 的注释。
10. **网络与容错**：10 秒超时、两次尝试、跟随系统代理、固定 UA；任何失败都只影响本次检查。请求只走 HTTPS，不携带凭据。
11. **发版流程**：`verify.ps1` 先行；断言 tag 名等于 `<Version>`、HEAD 就是该 tag、工作区干净；GitHub 用 `gh` 创建 Release 并上传 ZIP，Gitee 用令牌认证的地址推送 tag ref 后调 API 创建 Release 并上传 ZIP；各 host 的清单最后生成并上传。流程幂等（同一 tag 重跑只补齐缺失资产）。CI 主责：推送 `v*` tag 触发独立 release workflow 调用同一脚本；本地脚本只作补救，不负责建 tag。
12. **凭据与配额**：Gitee 私人令牌最小权限，只存在 Actions secret `GITEE_TOKEN` 或本地环境变量，日志掩码，绝不入库；Gitee 单附件 100MB、仓库附件总量 1GB，文档写明，脚本超过 80% 告警，不自动删除（不可逆，交由 owner 决定）。Gitee 仓库固定为公开的 `ZLiLiang/JiuMi`，需完成实名与公开仓库审核。
13. **信任模型**：清单只来自两个 HTTPS host，v1 无签名。最坏情况是把用户引到钓鱼页，而 v1 只做页面跳转、不静默执行，因此接受该风险。自动更新落地前必须引入独立于清单的完整性来源（代码签名 + 独立哈希），并在届时的 ADR 中重新评估。

## 为什么

- **双源是体验约束，不是冗余**：检查清单只有几百字节，但 ZIP 有约 75MB；只在 Gitee 放清单、ZIP 仍在 GitHub，会让「检查更新」变成推不动的按钮。双源发布让链接和内容落在同一个可达的 host 上。
- **固定 tag 的清单比仓库内文件可靠**：提交在 master 的 `update.json` 会和「版本号已 bump、Release 还没发」的中间状态脱节；固定 tag 的清单只在发布时改变，且与资产同生命周期。
- **通道跟随安装版本**：预览版用户是主动选择预览的，应该同时看到预览与正式；稳定版用户不应被预览版打扰。这比增加一个设置项更少认知负担。
- **只提示是当前风险最小的增量**：自包含目录正在运行时无法安全替换，且包未签名；先把通知与发布链路做对，自动更新等签名和安装器方案确定后再做。
- **检查状态与设置分离**：设置变更会推动界面的设置传播；把每天一次的检查时间写进设置文件会造成无意义的传播与设置文件抖动。
- **一次性排程而非轮询**：JiuMi 常驻托盘可能连开数周，只在启动时查会永远错过；但每小时轮询既费电也无意义，按到期时间排一次即可。
- **复用托盘气泡**：仓库已有 `IUserNotification` 与原生托盘实现，不需要为未打包应用注册 AUMID 或引入 Windows Toast。

## 备选与取舍

| 备选 | 为什么没选 |
| --- | --- |
| 直接调 GitHub REST API（`/releases/latest`） | 未认证 60 次/小时/IP；忽略预发布；国内 `api.github.com` 不稳定；静态资产无 API 限流 |
| 清单放仓库 master 并由镜像同步 | 与「版本已 bump、Release 未发」脱节；镜像滞后不可控 |
| 仅 GitHub 单源 | 国内下载近乎不可用，通知无法兑现 |
| 仅 Gitee 单源 | 审核与下架风险；1GB 附件配额；GitHub 用户仍需可用的源 |
| 所有人只看稳定版 | 预览版用户在下一个正式版前收不到任何提示 |
| 新增「接收预览版」设置 | 多一个用户需要理解的概念；跟随安装版本已足够 |
| v1 就做应用内下载 / 自替换 | 无签名、目录被占用、需要回滚；风险与收益不成比例 |
| Windows Toast | 未打包应用需要快捷方式与 AUMID 注册，工作量大，样式收益有限 |
| 每小时轮询 | 无意义的网络与电量开销；24 小时到期排程已覆盖常驻场景 |
| 检查时间存 settings.json | 触发设置变更传播，设置文件无意义抖动 |
| 「跳过此版本」 | v1 交互保持最小；关于页状态已能表达「有新版本」 |
| 自动清理 Gitee 旧附件 | 删除不可逆，且会破坏旧发版说明里的下载链接；只告警 |
| 本地脚本独占发版 | 门禁与一致性断言依赖人工执行；tag push 触发 CI 更可复现 |
| 由本地脚本创建 tag 并发版 | 与 tag-push 触发的 CI 冲突，可能重复发版 |

## 后果

正面：

- 国内用户能稳定收到更新提示并从 Gitee 下载；海外用户回退 GitHub。
- 预览版与稳定版用户各自得到正确提示，无需新增设置。
- 清单字段已为自动更新预留，后续不需要改发布协议。
- 发版由 tag 触发，门禁与一致性检查强制执行，重跑幂等。

负面（明确接受的代价）：

- 每个版本多上传约 75MB 到 Gitee；约 13 个版本后需人工清理旧附件。
- Gitee 公开仓库需要实名与审核，且存在被下架的可能；GitHub 兜底但不保证国内可达。
- v1 清单无签名，信任建立在两个 host 的 HTTPS 上。
- 单侧发版失败时该 host 的清单会落后，直到脚本重跑成功。
- 检查每天至多一次，新版本到被大多数安装感知最多滞后约 24 小时。

中性：

- 复用 ADR-0008 的「Release 资产 + 固定 tag」模式，但更新检查不落盘数据、不校验文件、不做原子缓存，是更轻的独立实现。
- 托盘气泡受托盘图标可用性限制；托盘不可用时只保留关于页状态。
- 新增文案进入 `zh-CN.json` 与 `en-US.json`。

## 不在本 ADR 内

- 应用内下载、文件替换、重启与回滚，以及安装器（MSIX/Inno）的迁移。
- 代码签名、签名校验与密钥管理。
- 增量更新、差分下载、CDN 或对象存储的进一步优化。
- Gitee 代码镜像的日常同步方式（发版脚本只推送 tag）。
- 「跳过此版本」、更新渠道设置、静默安装等产品交互。
